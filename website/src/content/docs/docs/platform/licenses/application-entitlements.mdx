This guide walks you through how to use Application Entitlements to control which application versions your end-customers can access and deploy through Distr controllers.

<Aside type="note">
  Application Entitlements are a Pro feature available in Pro, Enterprise, and
  Pro Trial plans. Learn more about [License
  Management](/docs/platform/license-management/) and [subscription
  plans](/docs/subscription-management/).
</Aside>

With Application Entitlements, you can link an entitlement to a customer to grant access to specific application versions, whether that's one version, a few, or all of them. You can name the entitlement, set an expiration date, and assign it to a particular customer. This gives you granular control over which applications and versions each end-customer can use.

## Use case

Many vendors offer tiered pricing plans with different features. For those serving [on-premises](/glossary/on-premises-definition/) environments, granular control over version access matters: you might deliver a specific feature set, send hotfixes to select customers, or offer early access to new application versions. Application Entitlements give you that control.

## Entitlement features

1. Each entitlement is linked to a single `customer/application` pairing.
2. Each entitlement grants a customer access to one or multiple application versions.
3. Once an application version has been granted via an entitlement, it can't be revoked (version revoking is currently in progress).
4. A customer can be associated with multiple entitlements.
5. Entitlement edits are reflected in the customer portal in real time.

## How to use it

If you don't see the feature yet, make sure you're on a Pro plan or Pro Trial. Once you're in, here's how it works:

1. **Create a customer:** If none exist, [create a customer](/docs/platform/customer-management/#creating-a-customer) first
2. **Navigate to Licenses** in the sidebar
3. **Click the customer** you want to create an entitlement for
4. **Select the Application Entitlements tab** and click **"Create Entitlement"**
5. **Give it a name**
6. **Set an expiration date** (optional)
7. **Assign to an application**
8. **Choose the versions**: grant all versions, or select specific ones and optionally an auto-add regex for future versions
9. **Save**: click "Save" and you're done

The customer can now access and deploy the assigned application version/s directly from their [customer portal](/docs/platform/customer-portal/).

## Choosing the granted versions

An entitlement grants either **All versions** of the application, which includes every version you create later, or **Specific versions**. With specific versions, you have to select at least one version, the customer only gets the versions you select and new versions are not added unless they match the [auto-add version regex](#auto-add-version-regex).

## Auto-add version regex

An entitlement for specific versions can grow with your releases. Enter a regular expression in **Auto-add Version Regex**, and every new application version whose name matches it is added to the entitlement automatically. For example, `^2\.\d+\.\d+$` keeps a customer on every `2.x.y` release without you editing the entitlement after each one.

### How matching works

- **When it runs:** The regex is checked whenever you create an application version and whenever you rename one. Setting or changing the regex does not touch existing versions, so select those yourself.
- **Renamed versions:** A renamed version is added if its new name matches and its previous name did not. A version you removed by hand is therefore not added back by a rename that keeps it matching.
- **Archived versions:** These are never added.
- **Syntax:** The regex uses [RE2 syntax](https://github.com/google/re2/wiki/Syntax) and may be up to 200 characters long. Lookaheads and backreferences are not supported.
- **Partial matches:** The regex matches anywhere in the version name unless you anchor it with `^` and `$`. Matching is case-sensitive; prefix the regex with `(?i)` to ignore case.
- **At least one version:** An entitlement with an auto-add regex needs at least one selected version, since an entitlement without versions already grants all of them.

An auto-added version is an ordinary entry of the entitlement. The customer can deploy it right away, it is considered for automatic updates and update notifications and you can remove it like any version you selected yourself. Renaming it to a name that no longer matches keeps it in the entitlement.

### Examples

| Regex             | Adds                           | Does not add             |
| ----------------- | ------------------------------ | ------------------------ |
| `^2\.\d+\.\d+$`   | `2.0.0`, `2.14.3`              | `12.0.0`, `2.1.0-rc.1`   |
| `^2\.`            | `2.1.0`, `2.1.0-rc.1`          | `12.0.0`, `v2.1.0`       |
| `^\d+\.\d+\.\d+$` | `1.4.2`, `3.0.0`               | `1.5.0-beta.1`, `v1.4.2` |
| `-lts$`           | `3.2.0-lts`                    | `3.2.0`, `3.2.0-lts.1`   |
| `^[23]\.\d+\.\d+` | `2.1.0`, `3.0.4`, `3.0.4-rc1`  | `4.0.0`, `1.2.3`         |
| `(?i)^release-`   | `release-2026-10`, `RELEASE-7` | `pre-release-1`          |

## OCI registry authentication

If your images are stored in a private [OCI registry](/glossary/oci-container-artifact-registry/), you'll need to provide access credentials. You can configure these credentials in the lower section of the entitlement configuration panel. Once set, the application versions will be available at the deployment target for as long as the entitlement is valid.
