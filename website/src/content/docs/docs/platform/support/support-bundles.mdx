Support Bundles give your customers a structured way to share diagnostic data when they report an issue. A customer initializes a bundle, runs a single `curl` command on their deployment host, and the collected data appears in your Vendor Portal. Nothing is uploaded without the customer's explicit approval.

<Aside type="note">
  Support Bundles are currently available for **Docker-based deployments only**
  on the Trial, Pro, and Enterprise plans. For access to Kubernetes Support
  Bundles, contact us at [support@distr.sh](mailto:support@distr.sh). The
  feature must be enabled per customer organization before customers can use it.
  See [Enabling features per
  customer](/docs/platform/customer-management/#enabling-and-disabling-features-per-customer).
</Aside>

## How it works

1. The customer creates a support bundle from the Customer Portal, giving it a title and optional description.
2. Distr generates a one-time `curl` command tied to that bundle. The command is valid for 24 hours.
3. The customer runs the command on the affected host. An interactive script launches and shows the customer exactly what will be collected: the available Docker containers, the environment variable groups (with redacted values already masked) and the source of every custom script you configured. The customer can exclude any containers, env var groups or scripts before anything runs or is sent.
4. Once the script finishes, the bundle appears in the Vendor Portal with all collected resources attached.
5. You and the customer can exchange comments on the bundle. When the issue is resolved, you mark it as resolved.

Every collected resource is limited to 1 MiB by default. Container logs keep the most recent output, script output the first, and a truncated resource says so in its content. On a self-hosted instance, the limit can be changed with [`SUPPORT_BUNDLE_RESOURCE_MAX_BYTES`](/docs/self-hosting/configuration/#support-bundles).

## Vendor setup

### Configure environment variables

In the Vendor Portal sidebar, navigate to **Support Bundles**, then click **Settings**. You can configure which environment variables should be collected from the host and containers. The script collects only the variables on this list. Variables marked as **Redacted** have their values replaced with `[REDACTED]` in the collected data. The customer sees the redacted placeholder before confirming the upload.

If no environment variables are configured, the script only collects container logs from running containers.

<ThemedImage
  lightSrc={settingsLight}
  darkSrc={settingsDark}
  alt="Support Bundle Settings showing the environment variable configuration"
/>

To add variables manually, click **Add Variable** and enter the variable name. To import from an existing file, click **Import** and paste the contents of a `.env` or config file. Lines in the format `KEY=value` or `KEY: value` are accepted; only the variable name is imported, not the value. Lines starting with `#` are ignored.

Toggle **Redacted** for any variable whose value should not appear in collected bundles.

Click **Save** when done.

### Configure custom scripts

Environment variables and container logs do not always answer the question you need answered. In the same **Settings** page you can add custom scripts that run on the customer's host during collection. Everything a script writes to standard output is attached to the bundle as a resource named after the script.

Click **Add Script** and give it a name, an optional description and the script body. The name is what the resource is called in the bundle and in the downloaded archive, so pick something you will recognise later, such as `database-status`. The description is shown to the customer next to the script.

A script runs with the interpreter named in its shebang, so `#!/usr/bin/env bash` gets you Bash. Without a shebang it runs with `sh`. Keep in mind that you are writing for the customer's host, not yours: check that a command exists before relying on it, and do not assume Bash is installed.

Use the **Enabled** toggle to park a script without deleting it. Disabled scripts are never sent to a customer.

<Aside type="caution">
  Custom scripts execute on infrastructure you do not control, so the customer
  is shown the full source of every script and can exclude any of them before
  anything runs. Write scripts that only read diagnostic state, and never
  include credentials in them — anyone who can collect a bundle can read them.
</Aside>

If a script fails or writes to standard error, its exit code and standard error are appended to the collected output so you can tell an empty result apart from a broken script.

### Enable the feature for a customer

Support Bundles must be enabled per customer organization before customers can create bundles. See [Enabling features per customer](/docs/platform/customer-management/#enabling-and-disabling-features-per-customer) for how to do this.

## Reviewing support bundles

In the Vendor Portal, navigate to **Support Bundles** to see all bundles across all customers.

<ThemedImage
  lightSrc={listVendorLight}
  darkSrc={listVendorDark}
  alt="Support Bundles list in the Vendor Portal"
/>

The list shows each bundle's title, customer, status, resource count, comment count, and when it was last updated. Click any bundle to open the detail view.

In the detail view:

- **Collected resources** are listed under **Resources**. Click any resource name to expand and read its content.
- **Comments** appear below the resources. Both vendor and customer users can leave comments.
- Click **Mark as Resolved** to close the bundle once the issue is addressed.

## Customer flow

When Support Bundles is enabled for a customer organization, customers see **Support** in their Customer Portal sidebar. For the full customer-side guide, see [Customer Portal Support Bundles](/docs/platform/customer-portal/support/).

## Bundle status lifecycle

| Status          | Meaning                                                                         |
| --------------- | ------------------------------------------------------------------------------- |
| **Initialized** | Bundle created, collection script not yet run. Secret valid for 24 hours.       |
| **Created**     | Collection script ran successfully. Resources are attached and ready to review. |
| **Resolved**    | Vendor has marked the bundle as resolved.                                       |
| **Canceled**    | Bundle was canceled before data was collected.                                  |

Either party can cancel an **Initialized** bundle. Only vendors can resolve a bundle. Once resolved or canceled, a bundle cannot be reopened.
