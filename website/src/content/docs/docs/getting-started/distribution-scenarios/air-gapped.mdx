[Air-gapped](/glossary/air-gapped-meaning/) deployments sit at the far end of the [self-hosted spectrum](/blog/self-hosted-spectrum/): the product runs in the customer's environment with **no vendor access** and no live path to your SaaS control plane.

Two problems to solve:

1. **Create a complete offline package** (application + every image and dependency).
2. **Move that package across the gap** (USB, exchange/staging server or another customer-approved transfer), then deploy inside the isolated network.

A Compose file or Helm chart alone is not enough. Images have to travel with the recipe, or be pullable from a place the customer is allowed to reach.

## True air-gapped deployments: Kubernetes with Zarf (recommended)

For Kubernetes, [Zarf](/docs/integrations/zarf/) is the path we recommend. A Zarf package is the offline bundle: Helm chart, container images, dependencies and SBOMs in one archive.

<Steps>

1. **Create the Zarf package with Distr.** Build it in CI (for example the GitHub Actions job in the [Zarf integration guide](/docs/integrations/zarf/#step-4-automate-with-github-actions)) so every release produces a versioned archive, then publish it to your Distr registry. Control who can pull which versions with [artifact entitlements](/docs/platform/artifact-entitlements/).
2. **Customer moves it across the gap** on a connected staging machine they control: pull the entitled package from Distr, then transfer via USB/removable media, an exchange/DMZ server or whatever one-way process they already trust.
3. **Deploy offline** inside the air-gapped cluster with `zarf package deploy` from the local archive. No vendor access, no pull from Distr at install time.

</Steps>

Commands, `zarf.yaml` and the full GitHub Actions example live in the [Zarf integration guide](/docs/integrations/zarf/). This use-case page is the model; that page is the how-to.

## True air-gapped deployments: Docker Compose

The offline bundle for Docker Compose is one archive with the Compose file and every image it references, built on a connected staging host with the script below.

**Vendor side.** Upload to Distr everything the app needs: the Compose file **and** every image it references (frontend, backend, Redis, Postgres, sidecars, …). Compose alone is not enough. If only Compose is on Distr, the customer would still have to pull images from somewhere else (often Docker Hub). Put all images on Distr, point Compose at those Distr image references and entitle the customer for those artifacts.

**Customer side.** On a connected staging host with Docker, Docker Compose and [ORAS](https://oras.land/docs/installation), log in with a [personal access token](/docs/integrations/personal-access-token/) and build the bundle.
Take the registry host and the artifact name of the Compose file from the [Customer Portal](/docs/platform/customer-portal/registry/).

```sh
#!/bin/sh
set -e

REGISTRY="registry.distr.sh"
COMPOSE_ARTIFACT="$REGISTRY/your-org/your-app-compose:1.0.0"
COMPOSE_FILE="docker-compose.yaml"
BUNDLE="your-app-1.0.0"

echo "$DISTR_ACCESS_TOKEN" | docker login "$REGISTRY" --password-stdin -u -

mkdir -p "$BUNDLE"
oras pull "$COMPOSE_ARTIFACT" --output "$BUNDLE"

docker compose -f "$BUNDLE/$COMPOSE_FILE" config --images > "$BUNDLE/images.txt"
while read -r image; do
  docker pull "$image"
done < "$BUNDLE/images.txt"
docker save -o "$BUNDLE/images.tar" $(cat "$BUNDLE/images.txt")

tar -czf "$BUNDLE.tar.gz" "$BUNDLE"
echo "Created $BUNDLE.tar.gz"
```

If the Compose file requires environment variables, set them or pass `--env-file` to `docker compose config`.
Add a [license key](/docs/platform/license-keys/) file or other configuration your application reads to the bundle directory before the `tar` step.

Transfer `your-app-1.0.0.tar.gz` across the gap, then deploy it inside the isolated network:

```sh
tar -xzf your-app-1.0.0.tar.gz
cd your-app-1.0.0
docker load -i images.tar
docker compose -f docker-compose.yaml up -d --pull never
```

Compose uses the `image:` names in the file, which match the images just loaded, so it never reaches a registry.
To serve the images from an internal registry instead, push them there after `docker load` and point the Compose file at it.

If the application needs Kubernetes and the air-gapped server has no cluster, see [Cluster Setup with k3s](/docs/integrations/k3s/#air-gapped-servers).

## Crossing the gap

How the package enters the isolated network is the customer's process. Common patterns:

- **USB / removable media:** download on a connected host, carry media in, deploy from local files.
- **Exchange / staging server:** download to a customer-controlled DMZ or jump host, then move through their approved transfer into the isolated network.
- **Data diode / one-way:** same idea: content only moves inbound under their controls.

## Restricted outbound to Distr (not a true air-gapped deployment)

If the customer allows outbound access **only** to Distr, the environment is restricted, not air-gapped. They authenticate and pull entitled Compose + images directly from your [Distr registry](/docs/registry/) (see the [customer portal registry](/docs/platform/customer-portal/registry/) flow), then run Compose there.

That only works when every `image:` in Compose points at Distr. If Compose still references Docker Hub (or another registry), whitelist Distr is not enough.

Prefer the true air-gapped paths above when there is no outbound path at all. Use restricted pulls when the buyer allows Distr but nothing else.

## Customer-hosted Distr

Some end customers run a [self-hosted Distr](/docs/self-hosting/) instance inside their own network so distribution stays inside their boundary. That is a special enablement path. Contact support@distr.sh if you need it.
