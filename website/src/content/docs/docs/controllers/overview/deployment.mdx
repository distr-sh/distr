This step-by-step guide shows you how to create deployments for Docker and Helm applications in Distr. Before creating a deployment, make sure you've already [created an application](/docs/controllers/application/) with at least one version. The deployment flow guides you through selecting a customer, choosing an application, configuring deployment settings, and obtaining the command to install both the Distr controller and your application.

<Aside type="note">
  If you're using application entitlements, make sure you've created the
  customer organization and assigned the entitlement before creating a
  deployment. Customers will only see applications they have entitlements for.
</Aside>

## Docker Deployment

### Step 1: Select Customer

Navigate to **Deployments** in the sidebar and click on the **+ New Deployment** button.

The first step is to select the customer organization that will receive this deployment, or your own organization for an internal deployment. If you haven't created any customers yet, you'll need to do that first. See [Onboarding a New Customer](/docs/platform/rbac/#inviting-customer-organization-users) for instructions.

<ThemedImage
  lightSrc={selectCustomerLight}
  darkSrc={selectCustomerDark}
  alt="Create New Deployment wizard on the Customer step with one customer selected"
/>

### Step 2: Select Application

After selecting a customer, choose the Docker application you want to deploy. You pick its version in the application configuration step.

<ThemedImage
  lightSrc={selectDockerApplicationLight}
  darkSrc={selectDockerApplicationDark}
  alt="Application step of the deployment wizard with a Docker application selected"
/>

<Aside type="tip">
  If an application doesn't appear in the list, it may be because: - The
  customer doesn't have an entitlement for that application - You need to create
  an [application entitlement](/docs/platform/application-entitlements/) and
  assign it to the customer first
</Aside>

### Step 3: Deployment Configuration

Give your deployment a descriptive name. This name will help you identify and manage the deployment later.

The same step sets up the Distr controller: autoheal for unhealthy containers, cleanup of old container images, a custom Docker endpoint, [log collection](/docs/controllers/logs-and-metrics/#container-logs) and [automatic controller updates](/docs/controllers/#controller-updates).

<ThemedImage
  lightSrc={dockerDeploymentConfigLight}
  darkSrc={dockerDeploymentConfigDark}
  alt="Deployment Configuration step with the deployment name and the controller options for Docker"
/>

### Step 4: Application Configuration

Pick the version to deploy and, where the customer has license keys, the license the deployment runs under. Then configure the environment variables for your Docker Compose application.

<ThemedImage
  lightSrc={dockerApplicationConfigLight}
  darkSrc={dockerApplicationConfigDark}
  alt="Application Configuration step with the version, the license and the environment variables of a Docker application"
/>

The entered environment variables will be passed unmodified to the `docker compose` process via the `--env-file` argument.
For more information on how to use them, please refer to [our guide on working with environment variables](/docs/controllers/docker-env/).

You can also enable Docker Swarm mode for deployments that should run in swarm mode. See [Docker Swarm](/docs/controllers/docker-controller/#docker-swarm) for more details.

### Step 5: Deploy

Click **Create Deployment** at the end of the application configuration. Distr creates the deployment and shows the command that installs the Distr controller in the customer's environment.

<ThemedImage
  lightSrc={dockerDeploymentCreatedLight}
  darkSrc={dockerDeploymentCreatedDark}
  alt="Deployment Created Successfully with the docker compose command that installs the Distr controller"
/>

<Aside type="caution">
  **Important**: This command will automatically install the Distr controller,
  which will then automatically install your application. The controller runs in
  the customer's environment and manages the full lifecycle of your application
  deployment.
</Aside>

## Verifying Your Deployment was successful

After running the command, you can check the deployment status in the **Deployments** section. Click on the status label to see the latest status of each revision, or on the **Inspect** button to view the [logs](/docs/controllers/logs-and-metrics/#log-viewer) of the deployment.

## Using Existing Deployment Targets

If you already have a deployment environment of type `docker` or `kubernetes`, you can use it to deploy your application.

Simply navigate to the **Deployments** section and click on the **+ Deploy App** button next to the deployment target you want to use.

<ThemedImage
  lightSrc={deployAppToTargetLight}
  darkSrc={deployAppToTargetDark}
  alt="Deployment target card with the Deploy App button next to its metrics"
/>

This opens a form where you pick the application and version and configure the deployment, as in the application configuration step above. The Distr controller of the target is already installed, so it picks up the new deployment without another command.

## Automatic Updates

A deployment can follow its application's latest version instead of being updated by hand or by a release pipeline. Distr then creates a new revision for it whenever the latest version changes, which is when a version is created, when an archived version is brought back, when the application's [versioning strategy](/docs/controllers/application/#versioning-strategy) changes and when an entitlement starts covering a newer version.

Open the actions menu on a deployment and select **Enable automatic updates**, or tick **Enable automatic updates** while creating or updating the deployment. Both a vendor and a customer can do this. Enabling it deploys the latest version right away, which is also why the version cannot be chosen while it is on.

A deployment is only ever moved forward. Archiving a version or narrowing an entitlement does not roll a deployment back to an older one, and neither does a version that the strategy orders below the one currently deployed.

A deployment whose values no longer apply to the new version is left on the version it runs, rather than being updated into a failing state. The same happens when the deployment is not entitled to the newer version.

The option requires **Allow automatic updates** on the application and is part of the Business plan.

## Deployment History

Distr keeps a full history of every deployment. Each time a deployment's version or configuration changes, a new revision is recorded, so you can always see what was deployed, when, and by whom.

On the **Deployments** page, open the actions menu on a deployment and select **Deployment history**. A timeline opens listing every revision, newest first, with the application version, the user or organization that made the change, and the timestamp. The active revision is marked **(current)**.

Select any revision to inspect its full configuration:

- **Docker**: the environment variables and deployment mode used for that revision.
- **Helm**: the values file, release name, and Helm options (wait strategy, rollback on failure, cleanup on failure, and force conflicts).

This makes it easy to review how a customer's deployment was configured in the past and to troubleshoot changes over time.
