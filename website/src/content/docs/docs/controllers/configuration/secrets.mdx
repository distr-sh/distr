Distr provides a centralized secret management system that allows you to securely store sensitive configuration values and reference them in your deployments using template syntax. The secret values are substituted at deploy time, so they never appear in your compose files, Helm values, or deployment logs.

<Aside type="note">
  This page covers Distr's built-in secret store, which works for both Docker
  and Kubernetes deployments. If you need secrets delivered as **files inside
  containers** rather than as environment variables, see [Docker Compose
  Secrets](/docs/controllers/docker-compose-secrets/), a Docker-native mechanism
  that can be used on its own or combined with Distr Secrets.
</Aside>

## What are Secrets?

Secrets are key-value pairs that store sensitive information such as API keys, passwords, database credentials, or any other confidential data that your application needs.
Instead of hardcoding these values in environment files or Helm values, you can store them centrally in Distr and reference them using template syntax.

For example, if your application needs a database password, you can create a secret with key `DATABASE_PASSWORD` and reference it in your deployment configuration:

```
DATABASE_URL=postgresql://user:{{ .Secrets.DATABASE_PASSWORD }}@host:5432/db
```

When the deployment is created, the template is automatically replaced with the actual secret value.

## Benefits of Using Secrets

- **Security**: Secret values are encrypted at rest and redacted from deployment logs; your deployment configuration can reference them via templates instead of storing them in plaintext
- **Centralized Management**: Update secrets in one place and have them automatically available to all deployments
- **Audit Trail**: Track who created or updated each secret and when
- **Access Control**: Secrets are scoped to organizations and customer organizations
- **Log Protection**: Secret values are automatically redacted from deployment logs, controller logs and [support bundles](/docs/platform/support-bundles/#redaction), along with common credential patterns

## Secret Scopes

Every secret belongs either to your own organization or to one customer. That decides which deployments can use it and where it is managed.

**Internal deployment secrets** are available to your internal deployments, which run on deployment targets without a customer. Distr never injects them into a customer's deployments. Use them for credentials that only your own infrastructure needs, such as a staging environment token. You manage them in the **Secrets** tab of your settings. See [Internal Deployment Secrets](/docs/platform/internal-deployment-secrets/).

**Customer secrets** are available only to the deployments of one customer, for example the customer's own database password. You manage them on the customer page, and the customer manages the same secrets in its Customer Portal. See [Customer Secrets](/docs/platform/customer-secrets/).

Both pages describe how to create, change and delete a secret.

## Using Secrets in Deployments

Secrets can be referenced in two types of deployment configurations:

### Environment Files (`.env`)

Use secrets in your environment files with Go template syntax:

```dotenv
# Reference a secret directly
API_KEY={{ .Secrets.API_KEY }}

# Use secrets in connection strings
DATABASE_URL=postgresql://user:{{ .Secrets.DB_PASSWORD }}@localhost:5432/mydb

# Combine multiple secrets
AUTH_TOKEN={{ .Secrets.CLIENT_ID }}:{{ .Secrets.CLIENT_SECRET }}
```

### Helm Values (YAML)

For Kubernetes deployments, reference secrets in your Helm values:

```yaml
database:
  host: db.example.com
  password: {{.Secrets.DB_PASSWORD}}

api:
  credentials:
    username: admin
    password: {{.Secrets.ADMIN_PASSWORD}}

config:
  githubToken: {{.Secrets.GITHUB_TOKEN}}
```

## Template Syntax

Secrets use Go's [`text/template`](https://pkg.go.dev/text/template) syntax for substitution.

### Basic Secret Reference

```
{{ .Secrets.SECRET_KEY_NAME }}
```

The secret key name must match exactly (case-sensitive) with a secret that exists in your organization.

### Conditionals

Use `if` statements to handle optional secrets:

```
API_URL={{ if .Secrets.API_URL }}{{ .Secrets.API_URL }}{{ else }}https://api.example.com{{ end }}
```

In YAML:

```yaml
api:
  url: {{ if .Secrets.API_URL }}{{ .Secrets.API_URL }}{{ else }}https://api.example.com{{ end }}
```

### Combining Secrets

You can combine multiple secrets in a single value:

```
CREDENTIALS={{ .Secrets.USERNAME }}:{{ .Secrets.PASSWORD }}
```

## Secret Naming Conventions

Secret keys must follow these rules:

- Must start with a letter (a-z, A-Z)
- Can contain letters, numbers, and underscores
- Cannot start with a number or underscore
- Cannot contain spaces or special characters (except underscore)

**Valid examples**:

- `API_KEY`
- `database_password`
- `GitHubToken123`
- `stripe_api_key_prod`

**Invalid examples**:

- `_API_KEY` (starts with underscore)
- `123_KEY` (starts with number)
- `API-KEY` (contains hyphen)
- `API KEY` (contains space)

## Security Considerations

### Log Redaction

Distr automatically redacts secret values from deployment logs. If a log message contains a secret value, it will be replaced with `********` before being displayed or exported.

This protects your secrets even if they accidentally appear in application logs.

### Secret Storage

Secret values are encrypted with AES-256-GCM before they are written to the Distr database, so a database dump
does not contain them. If you self-host Distr, the key is `DATABASE_ENCRYPTION_KEY`, see
[Security & Encryption](/docs/self-hosting/security#database-encryption) for how to store and rotate it. The
deployment values and env files that reference a secret are encrypted the same way.

To keep a value out of Distr entirely, create it in the customer environment and reference it by name, see
[External Secrets](/docs/controllers/security/external-secrets/).

### Access Control

- Only users with `read_write` or `admin` roles can create, update, or delete secrets
- All users in an organization can view secret keys (but not values)
- Secret values are never returned by the API after creation (only keys and metadata)

### Best Practices

1. **Rotate secrets regularly**: Update secret values periodically and redeploy affected applications
2. **Don't log secrets**: Ensure your application code doesn't intentionally log secret values
3. **Use descriptive keys**: Make it clear what each secret is for without revealing sensitive information
4. **Test in non-production first**: Verify secret references work correctly before deploying to production

## Error Handling

### Missing Secrets

If a deployment configuration references a secret that doesn't exist, the deployment validation will fail with an error:

```
template execution error: map has no entry for key "SECRET_NAME"
```

To fix this, create the missing secret or remove the reference from your configuration.

### Template Syntax Errors

If your template syntax is invalid, you'll receive an error during deployment validation:

```
template parsing error: unexpected "}" in operand
```

Check your template syntax for missing braces, quotes, or other syntax issues.

### Deleting a Secret in Use

Distr does not delete a secret that a deployment still references. The error names the deployment targets that use it, so you can remove the reference from their configuration first.

### Empty Secret Values

<Aside type="caution">
  Secret values cannot be empty. If you need to represent an empty value,
  consider using a placeholder string or removing the secret reference entirely.
</Aside>
