Services in one Compose file reach each other by their service names. Services in different applications don't, even on the same deployment target, because the Docker controller runs every deployment as a Compose project of its own (`distr-<short-deployment-id>`) with its own default network.

To connect them, one application creates a Docker network and the others join it.
This guide does that for a database and a backend that are deployed separately. The backend comes from [hello-distr](https://github.com/distr-sh/hello-distr), our example application.

- `networks.acme-shared.name` fixes the network's name. Without it, Compose puts the project name in front. That name differs for every deployment, so the others would not find the network. Replace `acme-shared` with a name unique to your application.
- `network` is a placeholder. Compose won't start a project that has no services, so the application needs one. The `pause` image does nothing and uses almost no resources.

## Step 3: Deploy the applications

Deploy all three applications on the same deployment target. For the first deployment, follow [Create a Deployment](/docs/controllers/deployment/). For the others, use **+ Deploy App** on the deployment target card.

<Steps>

1. Deploy the **Network**.

2. Deploy the **Database**.

3. Deploy the **Backend**.

</Steps>

If you deploy the database or the backend first, it fails with `network acme-shared declared as external, but could not be found`. The controller retries every cycle, so the deployment starts by itself once the network exists.

The backend's health check queries the database, so once the Database and Backend deployments are **Healthy**, the connection works. The Network deployment has no health check and stays **Running**. `http://<host>/latest-message` then answers with `hello distr!`.

## Address other deployments by a network alias

On the shared network, every container answers to its network aliases and to its service name. Service names tend to be generic, like `postgres` or `backend`. Two deployments can easily use the same one.
Docker then resolves the name to both containers in random order. Each request ends up at either of them.

- Give every service that other deployments connect to an alias under `networks.<name>.aliases` (like `acme-db`) and connect only through the alias.
- If one application is deployed more than once on a deployment target, build the alias from a deployment variable, for example `acme-db-${INSTANCE}`, so each deployment has its own. Do the same for published host ports, since only one deployment can bind the Backend's port `80`, for example `${HTTP_PORT}:5000`.

Leave services that no other deployment needs off the shared network.

## Keep the network definition stable

When a new version of the network application changes the network, for example by adding a label, a driver option or a subnet, Compose tries to recreate it. Docker can't remove a network that other deployments are still connected to, so the update fails with `network acme-shared has active endpoints`.
Settle the definition before the first deployment and keep it the same in every later version.

<Aside type="note">
  If you undeploy the network application while other deployments still use the
  network, Docker keeps the network and those deployments keep running. When you
  deploy the network application again, it takes over the existing network.
</Aside>
