Services in one Compose file reach each other by their service names. Services in different applications do not, even when they run on the same deployment target.
The Docker controller runs every deployment as a Compose project of its own, named `distr-<short-deployment-id>`, and every project gets its own default network.

To let deployments talk to each other, put them on a shared Docker network: one application creates it, and every other application joins it.
This guide connects a backend to a database that is deployed separately. The backend is the one from [hello-distr](https://github.com/distr-sh/hello-distr), our example application.

- `networks.acme-shared.name` gives the network a fixed name. Without it, Compose prefixes the network name with the project name, which differs for every deployment, so the other deployments would not find the network. Replace `acme-shared` with a name unique to your application.

## Step 3: Deploy the applications

Deploy all three applications on the same deployment target. For the first deployment, follow [Create a Deployment](/docs/controllers/deployment/). For the others, use **+ Deploy App** on the deployment target card.

<Steps>

1. Deploy the **Network**.

2. Deploy the **Database**.

3. Deploy the **Backend**.

</Steps>

A deployment that joins the network before it exists fails with `network acme-shared declared as external, but could not be found`. The controller retries it on every cycle, so it starts on its own once the network application is deployed.

Once all deployments are **Healthy**, `http://<host>/latest-message` answers through the backend, which reads the message from the database in the other deployment.

## Address other deployments by a network alias

On the shared network, a container can be reached by its network aliases and by its service name. Service names are often generic, like `postgres` or `backend`, and nothing prevents two deployments from using the same one.
When two containers on the network share a name, Docker answers with both addresses in random order and requests end up at either of them.

- Give every service that other deployments connect to an alias under `networks.<name>.aliases`, like `acme-db`, and only connect through the alias.
- If the same application is deployed more than once on a deployment target, take the alias from a deployment variable, for example `acme-db-${INSTANCE}`, so every deployment gets its own.
- Only the containers on the shared network can reach each other. A service that no other deployment needs stays on the default network of its own project.

## Keep the network definition stable

Compose recreates a network whose definition changed, for example when a new version of the network application adds a label, a driver option or a subnet. Docker cannot remove a network that other deployments are still connected to, so updating the network application to such a version fails with `network acme-shared has active endpoints`.
Decide on the definition before the first deployment and leave it unchanged in later versions.

<Aside type="note">
  Undeploying the network application while other deployments still use the
  network leaves the network in place, so those deployments keep running.
  Deploying the network application again takes the existing network over.
</Aside>
