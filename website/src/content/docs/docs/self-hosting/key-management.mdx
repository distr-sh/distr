By default `JWT_SECRET` and `DATABASE_ENCRYPTION_KEY` hold the key material itself. Both also accept a ciphertext
that the Hub unwraps with a configured key management service during boot, so the key material appears in neither your
configuration nor a Kubernetes Secret. Reading it becomes an API call that your cloud logs and that you can revoke
without touching the instance. Currently, the following KMS providers are supported:

- AWS Key Management Service (KMS)
- GCP Cloud Key Management Service (Cloud KMS)

KMS providers are configured via environment variables. Only one provider can be configured at a time; setting the
key of both is an error.

| Variable           | Required | Default | Description                                                                                                               |
| ------------------ | -------- | ------- | ------------------------------------------------------------------------------------------------------------------------- |
| `KMS_AWS_KEY_ID`   | for AWS  | —       | Key ARN, key id or `alias/<name>` of the AWS KMS key. Setting it selects AWS KMS.                                         |
| `KMS_AWS_REGION`   | no       | —       | Region of that key. Defaults to the region of `KMS_AWS_KEY_ID` when it is an ARN, then to the AWS SDK's own resolution.   |
| `KMS_AWS_ENDPOINT` | no       | —       | Overrides the AWS KMS endpoint. Intended for testing against a local stand-in.                                            |
| `KMS_GCP_KEY_NAME` | for GCP  | —       | Full resource name of the Cloud KMS key (`projects/…/locations/…/keyRings/…/cryptoKeys/…`). Setting it selects Cloud KMS. |

A wrapped value is the `kms:` prefix followed by the base64-encoded ciphertext:

```sh
KMS_AWS_KEY_ID=alias/distr
DATABASE_ENCRYPTION_KEY=kms:AQICAHhwPRWvSKbxYYqVjZ9…
```

The prefix is what tells the two apart, so a value without it keeps being used as it is and you can wrap one of the
two variables and leave the other. If the service is unreachable, or a ciphertext cannot be opened, the Hub refuses
to start rather than run without the value.

## Wrapping a value

What you wrap is the exact string you would otherwise put into the variable. A keyring of several keys is therefore
one ciphertext, and [rotating it](/docs/self-hosting/configuration#rotating-the-key) works exactly as it does for an
unwrapped key.

Every ciphertext is bound to the variable it is read for through the encryption context `distr=<variable>`. You have
to pass it when you wrap the value, otherwise the Hub cannot open it. It is what keeps a ciphertext made for
one variable from being used as another, and on AWS it can also be required by the key policy.

Write the value into `plaintext.txt` with `printf '%s' '<value>' > plaintext.txt`, and delete it, along with
`context.txt` on GCP, once you have the ciphertext.

With AWS KMS, the output is base64 already and goes behind `kms:` as it is:

```sh
aws kms encrypt \
  --key-id alias/distr \
  --plaintext fileb://plaintext.txt \
  --encryption-context distr=DATABASE_ENCRYPTION_KEY \
  --output text --query CiphertextBlob
```

With GCP Cloud KMS, `gcloud` writes raw bytes, hence the pipe:

```sh
printf 'distr=DATABASE_ENCRYPTION_KEY' > context.txt
gcloud kms encrypt \
  --location=europe-west3 --keyring=distr --key=distr-master \
  --plaintext-file=plaintext.txt \
  --additional-authenticated-data-file=context.txt \
  --ciphertext-file=- | base64 -w0
```

Both commands read the plaintext from a file rather than from an argument, so that it does not end up in your shell
history. See the [configuration reference](/docs/self-hosting/configuration#database-encryption) for the format each
variable expects.

## Permissions

The Hub only ever decrypts; wrapping a value is a one-time action you perform yourself, so its credentials do not
need permission to encrypt.

- **AWS**: `kms:Decrypt` on the key. You can restrict it to Distr by requiring the encryption context in the key
  policy, e.g. `"kms:EncryptionContext:distr": "DATABASE_ENCRYPTION_KEY"`. Credentials come from the default chain,
  so IRSA or an instance profile need no further configuration.
- **GCP**: `roles/cloudkms.cryptoKeyDecrypter` on the key. Credentials come from Application Default Credentials, so
  Workload Identity needs no further configuration and a service account key file is passed through
  `GOOGLE_APPLICATION_CREDENTIALS`.

<Aside type="caution">
  The key management service now holds what your data depends on. Losing the KMS
  key is losing the [database encryption
  key](/docs/self-hosting/configuration#database-encryption), and every value it
  protects with it. Provider-side automatic key rotation is safe, because every
  ciphertext records the key version it was made with.
</Aside>
