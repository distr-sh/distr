A Distr Hub holds two pieces of key material: the key its sensitive database columns are encrypted with, and the
secret its tokens are signed with. This page describes what each of them protects, what rotating it entails, and how to
keep either out of your configuration by storing it as the ciphertext of a key management service. Both are set as
environment variables, listed in the [configuration reference](/docs/self-hosting/configuration).

## Database Encryption

The Hub encrypts the sensitive columns of its database with AES-256-GCM before writing them: secret values, OIDC
client secrets, SMTP credentials, pull-through registry credentials, deployment value and env files, support bundle
resources, MFA secrets, Stripe webhook secrets and entitlement registry credentials.

`DATABASE_ENCRYPTION_KEY` is required and the Hub refuses to start without it. Generate one with
`openssl rand -base64 32`.

<Aside type="danger" title="Back up the key separately from the database">
  A database dump is worthless without the encryption key, and so is your data
  if you lose it. Keep the key somewhere that does not go down, or get deleted,
  with the database itself.
</Aside>

Instead of the key itself, the variable can also hold a ciphertext that the Hub unwraps with a
[key management service](#key-management-service) while it starts, so that no key material is kept in your
configuration.

Encryption is transparent, so nothing else in your configuration changes, but the values that were written before you
upgraded to a version with encryption are still in plaintext. Move them over in one of two ways:

- run [`distr maintenance encrypt-database`](/docs/self-hosting/maintenance#database-encryption) once, in a Hub
  container, or
- set `DATABASE_ENCRYPTION_MIGRATE_ON_BOOT=true` and restart the Hub, which does the same during startup. This is
  for single instance deployments only.

Either way it is safe to run while the Hub is serving traffic, and it can be interrupted and resumed. Until it has
finished, the Hub logs a warning on every start listing the columns that are still unencrypted. With more than one
replica, wait for the upgrade to roll out completely first, see
[Database Encryption](/docs/self-hosting/maintenance#database-encryption).

### Rotating the key

`DATABASE_ENCRYPTION_KEY` also accepts a comma-separated list of `<id>:<key>` entries, where the id is a number
between 0 and 255 and the first entry is the key that new writes are encrypted with. Every stored value records the id
of the key it was encrypted with, so the other entries are what keeps older values readable.

To rotate, put the new key first and keep the old one:

```sh
DATABASE_ENCRYPTION_KEY="1:<new key>,0:<old key>"
```

Then run `distr maintenance encrypt-database`, which re-encrypts every value that still uses the old key. Once it
reports nothing left to do, drop the old entry and keep only `1:<new key>`.

With more than one replica, put the new key on every replica before you make it active. A rolling update replaces
one replica at a time, so an updated one would otherwise seal writes with a key the others do not have yet, and
their reads of those values fail until the rollout finishes:

1. roll out `DATABASE_ENCRYPTION_KEY="0:<old key>,1:<new key>"`. The old key stays active, so nothing about how
   values are written changes, but every replica can read the new one.
2. roll out `DATABASE_ENCRYPTION_KEY="1:<new key>,0:<old key>"` to make the new key active.
3. run `distr maintenance encrypt-database` and drop the old entry as above.

## JWT Signing Secret

`JWT_SECRET` signs every token the Hub issues, with HS256: user sessions, the invite, password reset and email
verification links it sends out, and the access tokens agents call the API with. Generate it with
`openssl rand -base64 32`, and wrap it with a [key management service](#key-management-service) to keep it out of your
configuration as well.

There is no keyring for this secret, so replacing it invalidates everything signed with the previous one at once: users
are signed out and have to sign in again, and invite and password reset links that have been sent but not used stop
working. Agents recover on their own, because what their manifest carries is the access key of their deployment target,
which they exchange for a new token.

## Key Management Service

By default `JWT_SECRET` and `DATABASE_ENCRYPTION_KEY` hold the key material itself. Both also accept a ciphertext
that the Hub unwraps with a configured key management service during boot, so the key material appears in neither your
configuration nor a Kubernetes Secret. Reading it becomes an API call that your cloud logs and that you can revoke
without touching the instance. Currently, the following KMS providers are supported:

- AWS Key Management Service (KMS)
- GCP Cloud Key Management Service (Cloud KMS)

Which provider is used follows from the key you name: `KMS_AWS_KEY_ID` selects AWS KMS and `KMS_GCP_KEY_NAME` selects
Cloud KMS. Only one provider can be configured at a time; setting the key of both is an error. See the
[configuration reference](/docs/self-hosting/configuration#key-management-service) for both variables and for the
optional AWS region and endpoint overrides.

A wrapped value is the `kms:` prefix followed by the base64-encoded ciphertext:

```sh
KMS_AWS_KEY_ID=alias/distr
DATABASE_ENCRYPTION_KEY=kms:AQICAHhwPRWvSKbxYYqVjZ9…
```

The prefix is what tells the two apart, so a value without it keeps being used as it is and you can wrap one of the
two variables and leave the other. If the service is unreachable, or a ciphertext cannot be opened, the Hub refuses
to start rather than run without the value.

### Wrapping a value

What you wrap is the exact string you would otherwise put into the variable. A keyring of several keys is therefore
one ciphertext, and [rotating it](#rotating-the-key) works exactly as it does for an unwrapped key.

Every ciphertext is bound to the variable it is read for through the encryption context `distr=<variable>`. You have
to pass it when you wrap the value, otherwise the Hub cannot open it. It is what keeps a ciphertext made for
one variable from being used as another, and on AWS it can also be required by the key policy.

Write the value into `plaintext.txt` with `printf '%s' '<value>' > plaintext.txt`, and delete it, along with
`context.txt` on GCP, once you have the ciphertext.

With AWS KMS, the output is base64 already and goes behind `kms:` as it is:

```sh
aws kms encrypt \
  --key-id alias/distr \
  --plaintext fileb://plaintext.txt \
  --encryption-context distr=DATABASE_ENCRYPTION_KEY \
  --output text --query CiphertextBlob
```

With GCP Cloud KMS, `gcloud` writes raw bytes, hence the pipe:

```sh
printf 'distr=DATABASE_ENCRYPTION_KEY' > context.txt
gcloud kms encrypt \
  --location=europe-west3 --keyring=distr --key=distr-master \
  --plaintext-file=plaintext.txt \
  --additional-authenticated-data-file=context.txt \
  --ciphertext-file=- | base64 -w0
```

Both commands read the plaintext from a file rather than from an argument, so that it does not end up in your shell
history. The plaintext is what the variable expects unwrapped: a [keyring entry](#rotating-the-key) for
`DATABASE_ENCRYPTION_KEY`, the base64 secret on its own for `JWT_SECRET`.

### Permissions

The Hub only ever decrypts; wrapping a value is a one-time action you perform yourself, so its credentials do not
need permission to encrypt.

- **AWS**: `kms:Decrypt` on the key. You can restrict it to Distr by requiring the encryption context in the key
  policy, e.g. `"kms:EncryptionContext:distr": "DATABASE_ENCRYPTION_KEY"`. Credentials come from the default chain,
  so IRSA or an instance profile need no further configuration.
- **GCP**: `roles/cloudkms.cryptoKeyDecrypter` on the key. Credentials come from Application Default Credentials, so
  Workload Identity needs no further configuration and a service account key file is passed through
  `GOOGLE_APPLICATION_CREDENTIALS`.

<Aside type="caution">
  The key management service now holds what your data depends on. Losing the KMS
  key is losing the [database encryption key](#database-encryption), and every
  value it protects with it, so a backup of a wrapped value is only worth as
  much as the KMS key that opens it. Provider-side automatic key rotation is
  safe, because every ciphertext records the key version it was made with.
</Aside>
