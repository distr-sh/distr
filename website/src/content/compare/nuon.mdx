## Executive Summary

Distr and Nuon can both provision infrastructure and deploy applications inside
customer-owned cloud accounts.

Distr packages existing OpenTofu or Terraform configurations as versioned controller
images. Its infrastructure controller provisions and reconciles cloud resources, while
its Kubernetes controller deploys the application onto the resulting cluster.
Infrastructure and application releases use the same Distr distribution workflow.

Nuon provides a more opinionated operating model for vendor-managed BYOC on AWS,
Azure and Google Cloud. Its advantages include staged fleet rollouts, approval gates,
operational actions, release windows, break-glass access and integrated drift
remediation.

Distr fits vendors that want to reuse existing infrastructure automation, operate
customer-cloud installations themselves or let customers operate them and support
BYOC alongside Kubernetes, Docker, on-premises and air-gapped installations.

Nuon fits vendors whose BYOC operations depend on break-glass access, a dedicated
action framework, packaged approval workflows or release windows.

## The Short Answer

Choose Distr when:

- Existing Terraform or OpenTofu configurations should be reused.
- Infrastructure and application versions should follow one release workflow.
- BYOC is one of several required deployment models.
- Some customers provide an existing Kubernetes cluster or virtual machine.
- Docker, on-premises or air-gapped distribution is required.
- Customers may deploy through their own CI/CD pipelines.
- Software licensing and artifact entitlements are required.
- The vendor operates customer-cloud installations and also needs licensing, entitlements and a customer portal.
- Open-source code and platform self-hosting matter.

Choose Nuon when:

- Packaged staged fleet rollouts and approval gates are central requirements.
- Operational actions need a dedicated execution framework.
- Release windows and customer-approved updates are required.
- Break-glass access must be part of the platform.
- A packaged drift investigation workflow matters more than infrastructure portability.

## The Core Difference

### Distr Uses Versioned Infrastructure Controllers

Distr treats infrastructure as another versioned application.

The vendor packages an OpenTofu or Terraform configuration in an infrastructure
controller image. That controller runs inside the customer environment and provisions
the resources required by the application.

Those resources can include:

- Virtual networks
- Kubernetes clusters
- Managed databases
- Object storage
- DNS records
- IAM roles and policies
- Other resources supported by OpenTofu providers

The vendor publishes a new controller image when the infrastructure configuration
changes. Updating the Distr deployment rolls out the new infrastructure version.

The controller creates an OpenTofu plan, applies the required changes and records the
result in the deployment logs. Periodic reconciliation detects configuration changes
and infrastructure drift.

Distr can then use its Kubernetes controller to deploy the application onto the
provisioned cluster.

This creates a two-layer deployment:

1. The infrastructure controller provisions and reconciles the environment.
2. The Kubernetes controller installs and updates the product.

Distr manages both layers through versioned applications, customer deployments,
secrets, logs, health information and release controls.

### Nuon Uses a Dedicated BYOC Application Model

Nuon models the customer-cloud installation as a complete BYOC application.

The vendor defines the infrastructure, application components, inputs, policies,
actions and deployment behavior within Nuon's platform. A runner inside the customer
account executes the required operations with customer-controlled permissions.

Nuon coordinates the installation lifecycle through its control plane. Its operating
model covers infrastructure provisioning, application deployment, customer approvals,
operational actions and fleet management.

This approach gives vendors a structured system for operating installations across
many customer accounts on AWS, Azure and Google Cloud.

The tradeoff is a more opinionated platform model. Infrastructure and operational
workflows become part of Nuon's application structure rather than remaining independent
OpenTofu automation.

## Infrastructure Provisioning

### Reusing Existing Infrastructure Code With Distr

Distr works with standard OpenTofu and Terraform configurations.

A controller image contains:

- The infrastructure configuration
- The provider lock file
- The Distr OpenTofu controller
- Vendor-defined supporting files

OpenTofu installs the providers locked in that file when the controller runs. For
installations that cannot reach the public provider registry, vendors can mirror
providers into an OCI registry and point the controller at it.

Customer-specific values are passed through standard OpenTofu variables. Cloud
credentials remain inside the customer environment, for example as Distr secrets
consumed by the controller.

The infrastructure definition stays in the vendor's repository and remains compatible
with standard OpenTofu tooling. The vendor can test, review and run the same
configuration outside Distr.

This model fits vendors that already manage their SaaS or enterprise infrastructure
with Terraform or OpenTofu. Infrastructure engineers can keep using familiar modules,
providers, resource definitions and review processes.

### Using Nuon's BYOC Model

Nuon also supports infrastructure-as-code workflows, but it coordinates them through
its broader BYOC application model.

The platform connects infrastructure provisioning with application components,
installation inputs, actions, policies and rollout behavior.

This model provides more built-in operational structure. It also creates a tighter
relationship between the infrastructure workflow and the Nuon platform.

Nuon fits vendors that want the BYOC platform to define how the complete installation
operates.

Distr fits vendors that want existing OpenTofu automation to remain the primary
infrastructure definition.

## Updates and Drift

Both platforms can update infrastructure and detect drift.

Distr's OpenTofu controller periodically reconciles the declared configuration. It
creates a plan when the infrastructure version, variables or underlying resources
change.

The controller records resource changes in the deployment logs. A failed
reconciliation affects deployment health and can trigger an alert.

Distr can either reconcile the infrastructure automatically or run in plan-only mode.
In plan-only mode the controller logs the plan for review and does not apply it,
except for a confirmed destroy. The customer controls the controller's credentials and
permissions.

Nuon provides a more integrated day-two workflow around infrastructure changes. Its
platform is designed to help vendors review, approve, coordinate and remediate changes
across customer installations.

Nuon has the advantage when visual drift investigation and coordinated remediation are
central operating requirements.

Distr has the advantage when the declared OpenTofu configuration should remain
portable and automatic reconciliation is sufficient.

## Operating Customer-Cloud Installations With Distr

Distr also fits vendors that operate the installation in the customer's cloud
account themselves. The vendor runs both layers from the Vendor Portal:

- Infrastructure and application ship as versioned Distr applications and roll
  out through the same deployment workflow.
- Each customer deployment runs a specific version, and the vendor decides when
  it moves to the next one.
- Plan-only mode logs every infrastructure change for review before it is
  applied.
- Failed reconciliations show in deployment health and trigger alerts.
- Deployment logs and status cover the infrastructure and the application.
- Licensing, artifact entitlements, the OCI registry and the white-labeled
  Customer Portal are part of the same platform.

The customer keeps the cloud credentials and permissions. The vendor needs no
standing access to the account.

## Fleet Operations

Nuon's strongest differentiation appears after the initial installation.

Nuon provides packaged workflows for:

- Staged rollout groups
- Customer approval gates
- Release windows
- Pull-request plans
- Operational actions
- Break-glass access
- Installation-wide audit history
- Coordinated drift remediation

These capabilities support vendors that actively operate a fleet of customer
environments on AWS, Azure and Google Cloud.

Distr manages infrastructure and application versions across customer deployments.
Vendors can monitor deployment status, release updates, inspect logs, receive alerts
and control which version each customer can access.

Distr does not currently provide the same packaged operating model for staged BYOC
rollouts, temporary operational access and arbitrary actions across customer
environments.

Nuon is stronger when the vendor needs a dedicated operations platform for a large
BYOC fleet on AWS, Azure and Google Cloud.

Distr is stronger when the vendor wants a simpler controller model or expects
customers to retain more operational control.

## Security and Customer Control

Both products run components inside the customer environment.

Distr's infrastructure and deployment controllers receive only the credentials and
permissions required for their configurations.

The customer controls:

- Cloud credentials supplied to the controllers
- IAM policies
- Kubernetes permissions
- Infrastructure variables
- Controller deployment
- Registry access
- Update timing

The vendor does not require interactive access to the customer account.

Customers can also choose not to run a deployment controller. They can pull approved
artifacts from Distr and deploy them through their own CI/CD pipeline.

Nuon also uses an in-account runner with customer-controlled permissions. Its operating
model assumes that the vendor remains more involved in running the installation.

Nuon adds controls for that relationship, including release windows, customer
approvals, operational actions, audit history and break-glass access.

Distr fits environments where the customer may operate the deployment independently.

Nuon fits environments where the vendor operates the deployment under customer-defined
guardrails.

## Beyond BYOC on AWS, Azure and Google Cloud

Distr covers distribution models outside BYOC on AWS, Azure and Google Cloud.

The same platform can distribute software to:

- Customer-owned cloud accounts
- Existing Kubernetes clusters
- Docker hosts
- Linux virtual machines
- Private data centers
- Air-gapped networks
- Customer-managed CI/CD pipelines

Distr also provides the commercial distribution layer around those deployments.

That layer includes:

- Customer and application entitlements
- Authenticated OCI artifact distribution
- Version access controls
- Software license generation
- Offline license verification
- Vendor and customer portals
- Deployment health and logs
- Documentation and support workflows

These capabilities matter when customers have different security, infrastructure or
operating requirements.

A vendor can provision a new Kubernetes cluster for one customer, deploy into an
existing cluster for another and distribute Docker artifacts to a third. The same
customer, licensing and release model applies across those installations.

Nuon is more focused. Its platform is designed around vendor-operated applications
inside customer-owned accounts on AWS, Azure and Google Cloud.

That focus allows Nuon to provide deeper workflows for that BYOC operating model.
Distr's broader scope allows one platform to cover BYOC and traditional self-hosted
software distribution.

## When Distr Is the Better Fit

Choose Distr when the product must support several enterprise distribution models.

Distr is a stronger fit when:

- Existing OpenTofu or Terraform configurations should remain portable.
- Customers have different infrastructure requirements.
- Some customers expect the vendor to provision infrastructure.
- Other customers provide an existing cluster or virtual machine.
- Customers may require Docker or customer-managed CI/CD.
- On-premises and air-gapped installations are required.
- Software licensing must work without internet connectivity.
- Artifact and version access must be controlled per customer.
- The company wants an open-source, self-hostable platform.

Distr keeps infrastructure provisioning, application delivery, artifact access and
licensing within one customer and release model.

## When Nuon Is the Better Fit

Choose Nuon when the operations workflows it packages are central to a
vendor-operated BYOC service.

Nuon is a stronger fit when:

- Customers expect controlled, temporary vendor access to their accounts.
- Rollouts require staged installation groups.
- Customers must approve updates or define release windows.
- Operational actions must run across customer installations.
- Break-glass access needs a packaged workflow.
- Drift investigation and remediation are central platform functions.
- The company prefers Nuon's application model over maintaining independent controllers.

Nuon provides more packaged operating structure around vendor access, actions and
release coordination for customer-cloud environments.

## Final Comparison

Distr and Nuon overlap across infrastructure provisioning and application deployment,
but they optimize for different distribution strategies.

Distr packages infrastructure as portable OpenTofu controller images. It manages those
controllers alongside application deployments, customer entitlements, artifacts and
licenses.

The same Distr platform also supports existing infrastructure, Docker, Kubernetes,
on-premises systems, air-gapped environments and customer-managed pipelines.

Nuon provides a dedicated platform for vendors that operate applications inside
customer accounts on AWS, Azure and Google Cloud. Its strongest advantages are staged
fleet rollouts, approval gates, operational actions, release windows, break-glass
access and integrated drift operations.

Choose Distr when the vendor operates customer-cloud installations and needs
licensing, entitlements and a customer portal around them, when BYOC must coexist with
other self-hosted distribution models or when existing infrastructure automation should
remain portable.

Choose Nuon when break-glass access, a dedicated action framework, packaged approval
workflows or release windows are central to operating every customer installation.
